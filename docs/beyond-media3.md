# 超出 Media3 的部分：本專案特有的排程機制

Bili Extended 的幀排程以 Media3 1.8.1 的幀釋放規則為基礎（見 [media3-reference.md](media3-reference.md)），但 Bilibili 的 IJK 播放器和 Media3 結構不同：

- 影片幀經過「解碼程序 `:ijkservice` → 主程序的外部渲染 GL 執行緒 → SurfaceFlinger」三段；
- 畫面時間由 IJK 自己的 `frame_timer` 和音訊時鐘推動；
- 畫面在每個 App VSync 只重畫一次。

只照抄 Media3 時，有些問題它本來就不會遇到，所以沒有對策。本文列出本專案在 Media3 之外另外加的機制：每一項寫 Media3 怎麼做、這裡怎麼做、為什麼需要，以及實測的改善。

照抄 Media3 時踩到、修正後仍沿用 Media3 規則的坑，寫在 [bilibili-fix-guide.md](bilibili-fix-guide.md) 的 B 節，這裡只列 Media3 沒有的部分。

## 總覽

| 機制 | 適用情況 | Media3 的做法 | 改善（實測） |
|---|---|---|---|
| 交出相位鎖定 | 1x，內容間隔是整數格 | 依實際上一次交出的時間決定下一次 | 平板 120 fps 1x：總損失 8.2% → 4.4%，準時率 85% → 92% |
| 節奏鎖定 | 2x 以上、每格整數張的稠密倍速 | 每張都交出，由 SurfaceFlinger 取最新那張 | 穩定段奇偶翻轉每 8 秒 7–11 次 → 0 |
| 交出幀門檻 | 所有倍速 | 沒有最短交出間隔 | 1.5x 等非整數比例的均勻度、0.33x 在 48 Hz 面板上的對齊，都靠它 |
| 精確時間重新檢查 | 太早的幀 | 每輪約 10 ms 重新評估 | 0.5x：4／4 輪穩定（固定 2 ms 輪詢 2／4）；1x：4／4（3／4） |
| 稀疏內容保活 | 影片層每秒更新不到 50 次 | 沒有 | 4K60 的 0.25x／0.333x：準時率 69–88% → 97–100% |
| IJK 計時器卡死保護 | 所有倍速 | 沒有（Media3 沒有 IJK 的計時器） | 平板 1x、300 秒：約 500 ms 的停格 8 次 → 0 |
| 管線停頓後的追趕 | 停頓之後 | 距上次顯示超過 100 ms 才強制顯示 | 停頓後的畫面更快恢復；穩定段不變 |

「準時率」與「總損失」的定義見 README 的評分標準；以下數字都是同一台裝置、同一支片、開關交替的對照結果。

## 1. 交出相位鎖定（phase lock）

- **Media3**：下一幀何時交出，是從上一幀**實際**交出的時間往後推一格。
- **問題**：Bilibili 的外部渲染器在主程序，每個 App VSync 只畫一次，而且畫之前會用新到的幀蓋掉還沒畫的那張。從實際交出時間往後推，每次喚醒的誤差都會累加，幀的抵達時間像隨機漫步一樣在整個週期裡飄，一再越過「畫的那一刻」：4–5% 的幀從沒被畫出來，另有 2–3% 在 SurfaceFlinger 被取代。
- **做法**：把交出時間排在一個固定的格子上——第 k 格 = 主程序 App VSync ＋ 半格 − 「呼叫到抵達」的延遲，讓幀落在兩次重畫的正中間；每 n 格一幀（n = 內容間隔換算成的整數格數）。計畫依「**計畫中的**格子」前進，所以單次喚醒晚了，不會把下一次一起推晚。落後超過半格就重新對齊到現在，不會一口氣補送。
- **適用**：1x，而且內容間隔接近整數格（例如 120 Hz 面板上的 120／60／30 fps）。倍速時由節奏鎖定處理。
- **結果**：平板 120 fps 1x，總損失 8.2% → 4.4%，準時率 85% → 92%。
- **開關**：預設開，`debug.biliextended.phase=0` 關閉。

## 2. 節奏鎖定（cadence lock）

- **Media3**：內容比面板快時（例如 120 fps × 2 = 每秒 240 張，面板 120 Hz），每張都照時間戳交出，同一格裡由 SurfaceFlinger 取最新那張。
- **問題**：面板實際是 120.3 Hz 之類的非整數，和 240 張／秒每秒差約 0.7 張。排程用「改挑隔壁那張」吸收這個差，等於整個保留序列從偶數張跳到奇數張（奇偶翻轉），同一個運動看起來忽快忽慢。
- **做法**：固定保留同一組幀（例如每 2 張留 1 張，一直留偶數張），差額累積到一格時，讓同一張**多停一格**，相位不變。相位追隨聲音用時間常數 1.5 秒的 EMA（追太快時，IJK 偶爾超前約 230 ms 的單筆音訊位置會讓它連丟數張；中位數與快速追隨都試過，效果更差）。保留幀只有晚到超過「max(半格 + 3 ms, 晚到允許丟幀的設定值)」才丟。
- **刻意不做**：保留幀不套用交出幀門檻。試過（模組 204）之後，花瓣 10x 每輪多出 8–15 次「跳過 4 張」（不加時 0 次），因為被延後的那張會和下一張落在同一次重畫裡。
- **適用**：每格整數張（2 張以上）的稠密倍速。
- **結果**：穩定段奇偶翻轉從每 8 秒 7–11 次降到 0；手機與平板所有稠密組合都是 0。
- **開關**：預設開，`debug.biliextended.cadence=0` 關閉。

## 3. 交出幀門檻（handoff gate）

- **Media3**：沒有「兩次交出至少隔多久」的規則；每張依自己的時間戳交出。
- **問題**：IJK 會一次把圖片佇列裡的幾張連續送進排程。沒有最短間隔時，幾張可能擠在同一次重畫之間，只有最後一張被畫出來。
- **做法**：連續兩次交出至少隔「步距 − 1 ms」。步距的取法：
  - 內容比面板慢、而且內容間隔接近整數格時：步距 = 內容間隔（例如 0.5x 的 60 fps = 2 格）；
  - 內容間隔不是整數格時（例如 HyperOS 把面板降到 48 Hz 播 40 fps，一張 = 1.2 格）：步距 = 一格，讓顯示時間線把每張對到最近的格子，自然形成 1,1,1,1,2 的節奏。如果照內容間隔走，交出時間會逐漸偏離格子；
  - 內容比面板快時：步距 = 一格；多出來的幀由「同一格只留一張」的規則跳過。

  太早到的幀是**延後**而不是丟掉：它屬於後面的格子，丟掉會在每次交出後把整個佇列清空，2.5x–7x 時就達不到面板刷新率。
- **適用**：所有倍速，永遠開啟（相位鎖定的前提，也是 1.5x 這類非整數比例均勻度的來源）。

## 4. 精確時間重新檢查

- **Media3**：太早的幀留著，下一輪工作迴圈（約 10 ms 後）再評估一次。
- **問題**：IJK 的重新評估時間點是固定輪詢；太早的幀醒來的時刻和它該交出的時刻沒有關係，誤差最多一個輪詢週期。
- **做法**：太早的幀在「預定交出時間 − 就緒窗」那一刻剛好醒來再檢查；就緒窗預設 33 ms（面板上的「距離預定上屏多久才交出」）。固定輪詢間隔已移除。
- **結果**：0.5x 4／4 輪穩定（固定 2 ms 輪詢 2／4），1x 4／4（固定輪詢 3／4）。

## 5. 稀疏內容保活（keepalive）

- **Media3**：沒有對應的機制。
- **問題**：慢速播放 4K60（0.25x／0.333x，影片層每秒只更新 15–20 次）時，畫面上其他東西都不動，顯示管線在兩張之間進入閒置，下一張到時喚醒晚了，落到下一格。
- **做法**：影片層每秒更新不到 50 次時，每個 VSync 重畫一個 2 px、幾乎透明的小方塊，讓 SurfaceFlinger 每一格都合成。
- **結果**：4K60 0.25x／0.333x，12 輪交替對照（兩種順序），準時率從 69–88% 升到 97–100%；1x 不受影響。
- **開關**：`debug.biliextended.keepalive`：0 永不、1 永遠、未設定＝依上述條件。
- **已知限制**：目前這段程式寫在 fps 浮層裡，**只有開啟 fps 浮層時才會執行**（fps 浮層預設關閉）。README 的測試成果是在開啟 fps 浮層的狀態下量的。

## 6. IJK 計時器卡死保護（livelock guard）

- **Media3**：沒有這個問題——Media3 沒有 IJK 的 `frame_timer`。
- **問題**：排程用一份 IJK `frame_timer` 的鏡像計算回傳給 IJK 的延遲。鏡像偶爾落後 IJK 真正的 `frame_timer`，一張其實已經到期的幀每次都拿到正的延遲，一直不顯示，直到 500 ms 的逾時才放行，畫面停住約半秒。
- **做法**：到期的幀超過 30 ms 沒有顯示，就回傳最小延遲讓它立刻顯示，並把鏡像重新對齊。
- **結果**：平板 1x、300 秒，約 500 ms 的停格從 8 次降到 0。

## 7. 管線停頓後的追趕

- **Media3**：距上次顯示超過 100 ms 時強制顯示（`shouldForceRenderOutputBuffer`），在那之前晚到的幀照常跳過。
- **問題**：120 Hz 下 100 ms 是 12 格。管線停頓之後，追趕期間可能連續跳過很多張，畫面停得比停頓本身更久。
- **做法**：距上次顯示超過 2 格（120 Hz 約 16.7 ms，上限仍是 100 ms）就不再跳過，先顯示再追。
- **結果**：停頓後的畫面更快恢復；穩定段的上屏率不變（每秒 115.6–117.6 張）。

## 其他與 Media3 不同的地方

以下各項的細節寫在 [bilibili-fix-guide.md](bilibili-fix-guide.md)：

- **1x 提前量雙向鎖**（B.1）：鎖住「時間戳 − 實際送出時間」，只挪時間戳、不挪 IJK 的呼叫時間。
- **晚幀跳過的附加條件**（B.10）：降速後 1.5 秒內不跳；只有已解碼的幀在等待時才跳。
- **起播與暫停恢復的聲音位置**（B.8、B.12）：樣本不足時直接用已知的實際倍率；位置不動（暫停）就清空平滑環。
- **停用 Bilibili 的效能取樣**（B.5）：它和畫面通知共用執行緒，每次取樣讓畫面停 80–144 ms。
